## 1. Engine contract

- `internal/types/interfaces/agent.go:22-35` — `AgentEngine.Execute(ctx, sessionID, messageID, query string, llmContext []chat.Message, imageURLs ...[]string) (*types.AgentState, error)` plus `SetMemoryPrompt(prompt string)`. The engine is stateless across turns; history is loaded by the caller (`LoadAgentHistory`) and passed in (interfaces/agent.go:40-41; internal/agent/engine.go:30-34).
- `AgentStreamEvent` (interfaces/agent.go:12-19) is **dead/vestigial**: declared but referenced nowhere else in `internal/` (grep: only its own definition). The real in-flight contract is `event.Event` → `interfaces.StreamEvent` (see §2).
- `AgentService.CreateAgentEngine(ctx, config *types.AgentConfig, chatModel chat.Chat, rerankModel rerank.Reranker, eventBus *event.EventBus, sessionID, assistantMessageID string)` (interfaces/agent.go:42-49). Note: models and the EventBus are injected as live objects — the engine factory takes constructed interfaces, not IDs/keys.
- Implementation: `internal/agent/engine.go:35-64` (`AgentEngine` struct). `Execute` (engine.go:248-359): opens Langfuse span (280-298), builds system prompt incl. memory + model-context protocol (311, 133-144), builds messages from history (319), builds tool definitions (322), runs `executeLoop` (332); on error emits `EventError` to the EventBus (335-344).
- `executeLoop` (engine.go:428-510): bounded ReAct rounds (`withinIterationBudget`, engine.go:405-413; `MaxIterations < 0` = unlimited, internal/types/agent.go:97-108); ctx-cancel salvages partial tool results into a final answer (465-477); one compact-and-retry on context overflow per turn (engine.go:633-648); stuck-loop + empty-response guards (engine.go:661-678, 714-731); guarantees exactly-one `EventAgentComplete` via deferred emit, even on cancel (engine.go:449-457; internal/agent/finalize.go:192-218).
- Each round (`runReActIteration`, engine.go:534-765): think (LLM w/ function calling, 619) → analyze stop conditions (709-737) → act (`executeToolCalls`, parallel when `ParallelToolCalls` and ≥2 calls, internal/agent/act.go:219,245) → observe (append tool results to messages, 756). References accumulate on `state.KnowledgeRefs`; steps on `state.RoundSteps` (engine.go:302-307).

## 2. Event flow

- Vocabulary: `internal/event/event.go:16-86`. Agent streaming events: `thought`, `tool_call`, `tool_result`, `reflection`, `references`, `final_answer` (event.go:52-57); pipeline `agent.query/plan/step/tool/complete` (44-49); approvals `tool_approval_required`/`_resolved` (60-61); `mcp_oauth_required`/`_resolved` (67-68); `error` (71); `memory_recalled` (75); `context_compacted` (79); `session_title` (82); `stop` (85). EventBus is per-request, sync by default, `On`/`Emit` (event.go:126-183).
- `AgentStreamHandler` (internal/handler/session/agent_stream_handler.go:23-47) subscribes to 15 event types on the dedicated EventBus (112-129) and converts typed `event.*Data` payloads into `interfaces.StreamEvent` appended to the `StreamManager` (e.g. handleThought 132-177 → `thinking`; handleFinalAnswer 497-570 → `answer` with per-event-ID segments; handleComplete 650-801 → `complete`).
- `StreamManager` (internal/types/interfaces/stream_manager.go:23-33): append-only `AppendEvent` / offset-based `GetEvents`; impl is memory or Redis (1h TTL) chosen by env `STREAM_MANAGER_TYPE` (internal/stream/factory.go:14-31).
- HTTP/SSE: `POST /api/v1/agent-chat/:session_id` (internal/router/routes_chat.go:112-115) — the POST response itself is SSE: `handleAgentEventsForSSE` polls the StreamManager every 100ms and writes `StreamResponse` frames (internal/handler/session/stream.go:330-474; complete detection 404; stop detection 370-401). Resume endpoint: `GET /sessions/continue-stream/:session_id?message_id=` replays buffered events from offset 0, then continues polling (stream.go:35-204; route routes_chat.go:74). Embed channels: `/embed/:channelId/agent-chat` (frontend/src/composables/useEmbedChatSession.ts:304).
- SSE wire event names (`response_type`): internal/types/chat.go:201-253 — `answer`, `references`, `thinking`, `tool_call`, `tool_result`, `error`, `reflection`, `session_title`, `complete`, `artifacts_pending`, `tool_approval_required`/`_resolved`, `mcp_oauth_required`/`_resolved`, `memory_recalled`, `context_compacted`, `install_prompt`.
- Frontend consumes the POST SSE stream (frontend/src/api/chat/index.ts:44 posts to `/api/v1/agent-chat/:session_id`) and switches on `response_type` in frontend/src/composables/useChatStreamHandler.ts:554-849 (`thinking`, `answer`, `tool_call`, `tool_result`/`error`, `context_compacted`, approvals, oauth; references via data fields 145-147). `@microsoft/fetch-event-source` used for skill-install progress (frontend/src/composables/useConfigSkillInstallProgress.ts:2,70).

## 3. Sessions & persistence

- Models: `types.Message` (internal/types/message.go:254) with gorm columns `knowledge_references` (266), `agent_steps` jsonb (270), `is_completed` (283); repository at internal/application/repository/message.go.
- Timing: `Handler.executeQA` (internal/handler/session/qa.go:892-1078) — user message persisted (926), assistant message created **before** streaming with `IsCompleted:false` (935; qa.go:365), SSE wired (949), then `sessionService.AgentQA` runs in a goroutine (1003-1072). ## 6. dsh integration (`packages/dsh-weknora/`)

- **dsh = DeepSeek Harness** (`github.com/deepseek-ai/deepseek-harness`), an external agent harness CLI (README_CN.md:7-11; npm package `@deepseek-ai/dsh`, test/e2e/run-in-dsh.mjs:23,41). This repo's package `@wxg-prc-cpg/dsh-weknora` (package.json:2-5) is a **dsh plugin**: it gives dsh agents four tools that call INTO WeKnora's HTTP API (`weknora_list_knowledge_bases`, `weknora_search`, `weknora_read_document`, `weknora_ask` — README_CN.md:73-78). Read-only, no WeKnora writes (README_CN.md:100-101).
- Transport: plain REST/JSON over fetch with `X-API-Key` / `X-Tenant-ID` headers, plus SSE consumed from `weknora_ask` (`Accept: text/event-stream` on POST /knowledge-chat or /agent-chat) (src/client.ts:1, 127-128, 197-278, 301-303). Config via env (`WEKNORA_BASE_URL/API_KEY/...`) and dsh profile `cordis.patch.yml` (README_CN.md:26-54).
- Contract tests pin both sides: `contract/contract_test.go` asserts the plugin's request bodies decode into real Go handler types and the response/stream fields still exist (:75, :100-118, :124, :159, :226); `test/contract.test.mjs` + `test/fixtures/api-contract.json` assert the plugin only emits those calls (README_CN.md:152-154). e2e installs a real dsh from npm into a throwaway profile and runs headless against a mock WeKnora backend + deterministic model (test/e2e/run-in-dsh.mjs:72-88, 118-128).
- **The Go server does NOT invoke dsh anywhere today.** Grep for `\bdsh\b` across `internal/`, `cmd/`, docker-compose, config yields only substring false positives ("sprea**dsh**eet", e.g. internal/handler/session/attachment_processor.go:315). No exec/stdio, no binary, no config key. The package is an *inbound-consumer adapter* (dsh as agent runtime using WeKnora as a knowledge tool), i.e. evidence of the opposite direction from "WeKnora runs on dsh" — but it does define a stable, contract-tested subset of WeKnora's HTTP API an external runtime can already call.
